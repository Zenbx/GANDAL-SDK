# GANDAL SDK v0.3.0

**Date :** 2026-11-01 · **Version précédente :** 0.2.0 (non étiquetée, `e4d93b9`) · **Type :** mineure, avec changements incompatibles (version 0.x)

## Résumé

Cette version donne au SDK les mécanismes d'un SDK de cloud : identifiants
résolus automatiquement, relances, parcours des listes paginées, et attente
de l'état des ressources. Elle le rend aussi **vérifiable contre la vraie
iaas-api** : contrat OpenAPI, tests d'intégration et tests du paquet installé.
Ces tests réels ont révélé deux défauts qui empêchaient le SDK de fonctionner
avec l'API publiée ; ils sont corrigés.

## ⚠️ Changements incompatibles et migration

| Changement | Avant | Après | Action requise |
| --- | --- | --- | --- |
| Identifiants de profil | `ProfileOut.id: str`, `profile_id: str` | `int` partout (modèles et paramètres) | passer et comparer des entiers : `profiles.update(4, …)` |
| Identifiants de demande | `RequestOut.id: str`, `requests.get("req-1")` | `int` | `requests.get(12)`, `requests.accept(12)` |
| Code d'erreur sans enveloppe `{error}` | toujours `internal_error`, message = phrase HTTP | code déduit du statut (`401` → `unauthorized`, `404` → `not_found`…), message = `detail` | revoir tout test sur `err.code == "internal_error"` |
| Relances automatiques | aucune | 3 tentatives sur `429` ; sur `503` et erreur réseau pour `GET`, `PUT`, `DELETE` | rien ; pour l'ancien comportement : `GandalClient(url, retry=RetryPolicy(max_attempts=1))` |

Les deux premiers changements corrigent un défaut : avec les types de la 0.2.0,
ces appels échouaient de toute façon contre la vraie API (voir Corrections).

## Nouveautés

**Identifiants sans les écrire dans le code.** Ordre : arguments, puis
`GANDAL_ENDPOINT` / `GANDAL_TOKEN`, puis profil de `~/.gandal/credentials`
(`GANDAL_PROFILE` ; un profil demandé mais absent est une erreur).

```python
client = GandalClient.from_env()
admin = GandalClient.from_env(profile="admin")
```

**Relances** (`RetryPolicy`) : attente exponentielle avec gigue, `Retry-After`
respecté. Un `POST` ou `PATCH` n'est rejoué sur `503` ou erreur réseau que s'il
porte un en-tête `Idempotency-Key`, pour ne jamais créer de doublon.

**Pagination** : `paginate` parcourt toutes les pages de n'importe quelle
méthode de liste, page par page à la demande.

```python
for vm in paginate(client.orchestration.vms.list, project_id, state="running"):
    ...
```

**Waiters** : attendre un état, avec échec immédiat sur un état sans issue.

| Waiter | Succès | Échec immédiat | Défaut |
| --- | --- | --- | --- |
| `vms.wait_until_running` / `wait_until_stopped` | état atteint | `error`, `deleting` | 5 s × 60 |
| `vms.wait_until_deleted` | `404` | `error` | 5 s × 60 |
| `storages.wait_until_deleted` | `404` | – | 5 s × 60 |
| `requests.wait_until_accepted` | `accepted` | `refused`, `cancelled` | 15 s × 240 |

`unknown` n'est jamais un succès. Exceptions : `WaiterFailure`, `WaiterTimeout`
(toutes deux `WaiterError`, avec `last_value`).

**Typage** : le paquet livre `py.typed`.

## Corrections

- **`profiles.list()` et toute lecture de profil ou de demande échouaient**
  contre la vraie API avec une erreur de validation. Cause : l'API renvoie des
  identifiants entiers (`API_ENDPOINTS.md` §2), le SDK attendait des chaînes.
  Détecté par le nouveau test de contrat OpenAPI.
- **Les erreurs de l'API arrivaient toutes en `internal_error`.** Cause :
  iaas-api renvoie pour l'instant le format FastAPI `{"detail": …}` et non
  l'enveloppe documentée. Conséquence : `wait_until_deleted` n'aurait jamais
  reconnu une suppression terminée. Détecté par les tests contre la vraie API.
- **Licence** déclarée au format SPDX ; l'ancien format aurait fait échouer la
  construction du paquet à partir de février 2027.

## Limites connues

- iaas-api ne publie encore que l'authentification et les profils (10
  opérations). Les helpers des projets, VMs, stockages, réseaux, partages,
  packs et demandes suivent `API_ENDPOINTS.md` et ne sont vérifiés que par
  mocks ; ils seront testés contre l'API à mesure qu'elle les publie.
- `orchestration.health()` appelle `/api/v1/health`, absent de l'API actuelle
  (`404`).
- Les waiters des VMs dépendent de la mise à jour de `state` par le backend à
  partir de l'hyperviseur, pas encore branchée côté iaas-api.
- Le SDK n'envoie pas encore d'`Idempotency-Key` : le serveur ne les gère pas.
- Les cellules (IAM, hyperviseur, réseau, stockage, DNS, notifications) restent
  des stubs.

## Retours à faire aux autres équipes

À l'équipe iaas-api :

- les erreurs suivent le format par défaut de FastAPI et non l'enveloppe
  `{error: {code, message, details}}` de `API_ENDPOINTS.md` §1.4 ; le SDK s'y
  adapte, mais les clients ne peuvent pas distinguer `conflict` de
  `invalid_state`, qui partagent le statut `409` ;
- `/api/v1/health` n'est pas implémentée ;
- les dépendances ne sont pas épinglées : une nouvelle FastAPI modifie
  l'OpenAPI publiée sans changement de code ;
- les propositions de `docs/CONVENTIONS_API.md` (idempotence, `/operations`,
  `429`, `X-Request-Id`, GRN) sont à valider.
